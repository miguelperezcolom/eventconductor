# Global Enterprise QA Production-Ready Standard (Agnostic)

For any mission-critical application handling millions of daily transactions at the production frontline of a global enterprise, **failure is not an option**. Stability cannot be "patched" post-deployment—it must be mathematically and empirically proven before release.

To certify an application as production-ready for this scale, it must pass five rigorous, agnostic QA validation tiers.

---

## Tier 1: Functional Integrity & Regression Gating
Before testing load or failure, the application's logical correctness must be guaranteed across all components and API boundaries.

### **1.1 Automated Code Coverage & Static Analysis**
*   **Honest Coverage Floor:** Minimum **80% branch coverage** across all core business logic modules. Autogenerated classes (DTOs, serializers, clients) must be explicitly excluded from metrics to prevent false coverage inflation.
*   **Static Security Analysis (SAST):** Zero high or critical vulnerabilities identified by tools like SonarQube, Trivy, or Snyk.
*   **API Contract Validation:** Every REST, gRPC, or GraphQL endpoint must automatically validate its incoming payload against strict schemas (OpenAPI, JSON Schema, Protobuf).

### **1.2 Multi-Tenant & Backward Compatibility Testing**
*   **DB Migration Compatibility:** Schema upgrades must be 100% backward-compatible (supporting "Blue/Green" or "Rolling" deployments where older code runs alongside a newer database schema).
*   **Zero-Downtime Rollovers:** Validate that definitions, formats, and serialized states stored in the database by older versions of the app can be read, processed, and updated by the new version without corruption.

---

## Tier 2: Durability, Resiliency & Chaos Engineering
Production networks, databases, and physical hosts fail. Resilience testing is the empirical proof that the application **self-heals without losing data**.

### **2.1 Chaos Injection Gates**
The application must execute under active load while the following infrastructure failures are aggressively injected:
*   **Component Kill:** Random, abrupt killing of application pods/processes.
*   **Node Eviction:** Graceful and ungraceful draining of physical virtualization nodes.
*   **Downstream Loss (Database/Broker):** Abrupt cutting of connections to the database, caching layer, or message broker for up to 90 seconds.
*   **Network Degeneracy:** Injection of packet loss (minimum 10%) and network latency (minimum 500ms) between the application and its storage layers.

### **2.2 Agnostic Verification Invariants (The Resilience Laws)**
Upon healing the injected chaos and draining the system backlog, the following database invariants must hold perfectly:
*   **Conservation of Records:** No entity, record, or message is lost.
*   **Exactly-Once Processing:** No transactional operation or state change has executed more than once (deduplication or locking behaves correctly).
*   **Outbox/Queue Drain:** Once the load stops and infrastructure recovers, all transaction queues and outboxes must drain cleanly to exactly **0** pending items.

---

## Tier 3: Hardening & Sandbox Security
Frontline applications are continuously subjected to accidental bad input, malformed payloads, and malicious penetration attempts.

### **3.1 Parser & Sandboxing Security**
*   **StackOverflow Protection:** Any dynamic expression engine (JEXL, SpEL, script engines) must enforce strict limits on bracket nesting (e.g., maximum depth of 64) and length to prevent nesting-depth stack exhaustion from killing execution threads.
*   **Reflection & Sandbox Boundaries:** Dynamic script execution must block all access to Java/OS reflection layers (e.g., preventing access to `Class`, `ClassLoader`, `Runtime`, or `System`).
*   **Safe Failure Modes:** Any evaluation crash within a script or expression must fail *closed* (throwing a caught exception that parks the specific request), rather than throwing a JVM `Error` that unwinds the underlying daemon thread.

### **3.2 Input Boundaries & Mass Assignment**
*   **Payload Size Ceilings:** Strict HTTP request body byte caps (e.g., max 16 MiB) must be enforced at the gateway/servlet level to prevent memory exhaustion attacks.
*   **Undeclared Key Dropping:** When processing form or payload submissions, the application must drop all fields not explicitly declared in the target schema (blocking mass-assignment parameter-injection exploits).
*   **Constant-Time Comparisons:** Any security token, signature, or API key verification must use constant-time array comparison to prevent side-channel timing attacks.

---

## Tier 4: Performance, Soak & Scale Saturation
A production-ready application must operate with stable memory, disk, and CPU utilization under prolonged high load.

### **4.1 Throughput & Latency Floor**
*   **Baseline Calibration:** The application must maintain its target transaction throughput (e.g., 1,000 requests/second) under the configured database flush (`fsync`) and network latency limits.
*   **Thread & Connection Pool Integrity:** Connection pool metrics (like HikariCP or DB pools) must show that active connections never block indefinitely under peak load, and idle connections return to baseline cleanly during lulls.

### **4.2 The 24-Hour Soak (Memory Leak Detection)**
*   **Prolonged Load:** The application must run under continuous high load for a minimum of 24 hours.
*   **Heap Analysis:** JVM Garbage Collection (GC) pauses must stay in the millisecond range. The JVM heap utilization must exhibit a clean "sawtooth" pattern (completely returning to its baseline after full garbage collections), proving there are zero active memory leaks.
*   **Disk Constraints & Log Rotation:** Validate that high-frequency logs rotate automatically, ensuring log output never fills the system disk partition.

---

## Tier 5: Observability & Production Transparency
An enterprise application cannot be a black box; it must emit standardized telemetry to allow centralized monitoring teams to detect, diagnose, and resolve anomalies in seconds.

### **5.1 OpenTelemetry & Tracing Standards**
*   **Distributed Trace Propagation:** Every incoming request (via HTTP, gRPC, or message queue) must carry a unique W3C traceparent. The trace must propagate across all microservices and background worker threads, mapping the entire call execution path.
*   **Database Query Correlation:** Trace contexts must be injected as comments into SQL queries to let DBAs isolate slow queries back to the originating user request.

### **5.2 Metrics & Alerts (Prometheus/Grafana)**
The application must expose standardized Prometheus/OpenTelemetry endpoints (`/actuator/prometheus`) tracking:
*   **Golden Signals:** Latency, Traffic (requests/s), Errors (5xx vs 2xx), and Saturation (thread pool and queue depths).
*   **Surgical Healthchecks:** Custom, non-blocking healthcheck probes distinguishing between *Liveness* (is the process alive) and *Readiness* (is the process ready to accept database/broker traffic, bypassing disk-space or memory alarms).
